# AliceBot Plus 源码调研记录

> 调研日期：2026-09-12。对象：`../../AliceBot Plus` 当前工作区源码。本文区分现有实现、静态分析推断及 Forest 设计建议；未启动 Bot，未读取 API 密钥、WebUI 用户凭据、聊天归档或用户画像内容。未发现适用的 `AGENTS.md`。行号以本次阅读的源码为准。

## 1. 对新框架最有价值的结论

AliceBot 已贯通 OneBot 接入、消息编解码、异步插件调用、Agent 工具、富媒体渲染、上下文归档及运维界面，适合作为应用能力和适配器行为的参考。其热重载、并发与权限仍依赖进程内约定，不能直接作为重型微内核的可靠性边界。

当前记忆模型主要是按群组织的对话与向量库，存在独立的共享画像文件目录；它尚未形成“每个 Bot 有自己的全局记忆域”。Forest 应复用能力分层，重新定义 Bot、会话、运行、模块实例与资源的所有权。

## 3. 模块与生命周期：可继承的入口，需重建的保证

### 3.1 可以继承

- 将协议 API、消息编解码、渲染器、提示词和业务插件分成可替换模块，避免只有业务插件能更新。
- 用创建、销毁及重载前后钩子表达资源初始化和状态转移需求。
- 通过模块元数据声明启用状态、执行优先级和权限要求，并提供统一的管理入口。

### 3.2 静态分析发现的边界问题

1. **重载未保留可回滚的旧实例。** `load_module` 在 121–128 行删除全局缓存与旧实例，之后才在 135–150 行构造并执行新模块；加载失败在 159–161 行返回 `None`。当新代码语法错误或初始化失败时，旧服务可能已经不可发现。Forest 需先 prepare 新代，健康检查通过后才原子切换注册表。
2. **模块身份仍污染进程全局。** 121–124 行用 `if module_name in key` 删除 `sys.modules` 条目，141 行又用简单模块名注册。调用者私有 `instances` 不能保证完整依赖隔离；同名模块、多个 Bot 和多级加载器可能互相影响。Forest 应用不可变模块制品标识和带 generation 的实例标识。
3. **生命周期与业务调用不共享排空协议。** watcher 在线程中执行重载回调（46–75 行）；事件处理在 asyncio 任务中继续执行。chat 的锁只包住重载前后读写（2360–2408 行），业务处理入口（2631 行起）没有对应锁或在途租约。运行中的旧任务可能继续修改旧状态、使用失效资源。需要内核统一封闭入口、跟踪在途调用、协作取消和 generation 校验。
4. **注入参数/回调是加载器级可变字段。** `moduleloader.py` 103–105 行覆盖 `self.kwargs` 与回调，而非按模块保存；后续 watcher 用这些字段重载所有模块。不同依赖的初始化参数不宜依赖“最后加载模块”的上下文。
5. **资源释放不具备完整的显式所有权。** `Bot.destroy()` 调插件销毁和浏览器关闭后将加载器置空（538–561 行）；加载器停止 watcher 主要在 `__del__` / `__exit__`（204–214 行）。框架无法证明每个后台线程、子任务、连接、文件都已结束。Forest 应强制注册 ResourceScope，卸载不依赖垃圾回收。
6. **重连与 Bot 创建混在一起。** `server()` 每次连接成功调用 `bot.create()`，仅主循环终止后统一 `destroy()`（376–407 行）。连接重建应只更新适配器 session，不应默认重建 Bot 及其插件资源。

补充：管理命令在 `bot.py` 137 行调用 `reload_module()`，但本次阅读的 `ModuleLoader` 仅定义 `load_module()`，未定义该方法。文件变更触发的自动重载与管理命令不是同一条可靠控制路径。

## 4. 多 Bot 与多群异步语义

已有接收循环为每条消息启动独立异步任务，因此不同群的请求能够交错执行；同一个群的多个请求也会并行。每个请求创建单独 Agent 处理器（`chat.py` 2800–2818 行），可参考这一“运行独立”的方式。

但当前源码没有体现按 Bot/会话有界队列、公平调度、在途数量上限、同会话提交次序、输入去重和输出幂等。`create_task` 可持续增长；两个同群请求可能读取重叠历史、先后生成并以完成顺序写入；归档裁剪跨 `await` 修改同一列表。多个 Bot 若直接扩展现有列表，仍共享协议账号及默认文件路径。

Forest 的设计约束应是：

- `bot_id` 标识人格、政策、工具授权与全局记忆的所有者；`adapter_account_id` 标识平台连接账号；二者通过显式绑定关系关联。
- `conversation_id` 标识回复目的地与局部对话顺序；它可以包含平台群标识，但不决定长期记忆的存储分区。
- 对 `(bot_id, conversation_id)` 建立有界会话队列；不同会话可同时运行。同一会话的默认策略可以是单个活跃回复运行，后续消息进入队列或被可追踪地合并。
- Bot 全局记忆必须支持多个会话同时读取，并通过短事务、版本检查及幂等写入提交结果；不能用一个跨模型调用的大锁串行整个 Bot。
- 运行必须固定 `run_id`、目标会话、输入事件、记忆快照版本和策略版本；工具及最终输出沿此路由返回，不能从可变的“当前群”变量推断目的地。

## 5. 通信、权限与故障处理

### 5.1 保留的能力形态

OneBot echo 关联请求/响应、结构化消息编解码和音频分开发送是适配器可参考的行为。`Skip` / `SkipFollow` 体现了“忽略”和“消费”的需求，可改为类型化处理结果。超时、限流、异常收集和任务可视化也应成为公共服务。

### 5.2 需要提升为强制约束的部分

| 当前证据 | 对 Forest 的要求 |
| --- | --- |
| `OneBotAPI._make_request()` 轮询等待，无请求 deadline；关闭后仍索引字典（21–30 行） | 用有期限的 pending request 表/Future；断线、取消、重载时统一完成失败并清理；连接 epoch 防止旧响应误投 |
| `get_bot_group_list(async_mode=False)` 自己调用 `ws.recv()`（47–60 行） | 每个连接只有一个接收者；调用模块只提交请求，不直接消费传输流 |
| 插件上下文注入完整 `bot_entity` 和依赖目录，处理器接收 ws（`bot.py` 220–254、412–473 行） | 仅暴露稳定服务句柄、消息信封和经过收缩的能力上下文，禁止跨模块持有实现对象/原始连接 |
| 权限主要是插件 USER/ADMIN 与 `#sudo` 的 sender 检查；`#context` 读写全局缓存入口没有自身管理员检查（`chat.py` 2589–2628 行） | 管理命令、记忆读写、插件生命周期和平台副作用在相同授权入口做检查，明确 Bot、资源、主体与动作范围 |
| `ban_user` 的实现只校验参数与群存在；`onebot_v11_api_call` 直接执行传入字典（`chat.py` 1551–1615 行） | 工具声明不是授权。执行时绑定可信调用主体，检查具体动作、目标群、权限、预算与审计，禁止通过通用 API 绕过策略 |
| 文件读写直接使用 `profile_path / filename`（`chat.py` 1471–1497 行） | 文件能力按 Bot 命名空间封装；解析规范路径并限制根目录，使用版本写入/原子替换 |
| 插件处理异常记录后继续（`bot.py` 247–260 行），部分错误原文发送群聊（`chat.py` 3025–3026 行） | 定义业务拒绝、可重试、不可重试、超时、取消、结果未知等错误；内部详情保留在受控诊断通道 |

其他具体信号：插件优先级插入逻辑先按高值在前，再整体 `reverse()`（`bot.py` 224–234 行），与 README 的“越高越先执行”描述不一致；接收循环每次迭代将 `timeout_count` 置零（`__main__.py` 128、211–220 行），连续超时阈值难以累计。这说明新框架应把次序和故障状态写成可验证的契约。

群聊管理入口还存在次序耦合：[`entity/bot.py`](../../AliceBot%20Plus/alicebot/entity/bot.py) 的 220–258 行先依次等待业务插件，`SkipFollow` 可以提前返回，直到 269–279 行才分派 `#sudo/#plugin`，因此静态控制流允许普通插件阻塞或吞掉管理消息。`#sudo` 在 157 行检查管理员；`#plugin` 对应的 76–145 行入口没有 sender 参数或独立管理员检查。Forest 的[群聊 Shell](09-group-shell-command-system.md)保留 AliceBot 在聊天中运维的便利性，但把确定性管理路由放在任意插件之前，分别定义命令优先级、目标权限和独立回执队列。

WebUI 的 `/ws/ws-warpper` 在 47–92 行直接代理用户给出的 URL，未走登录检查；日志页使用 query 参数传入登录字段，登录失败路径记录 password（250–285 行）；已认证的 `restart` 命令直接调用宿主重启（874–876 行）。这些是源码中可见的权限边界问题，不是对部署状态的推断。Forest 运维界面应只调用控制面 API，授予范围受限的管理权限，并对凭据和聊天内容进行日志脱敏。

## 6. 记忆与 Agent 拆分建议

AliceBot 的上下文合并、媒体保留、超长内容归档和按请求构造 Agent 有实际参考价值。但 `chat.py` 同时实现存储、检索、工具注册、网络、平台管理、输出解析、渲染与命令处理，修改任一能力会扩大重载范围。

建议形成如下独立服务契约：

1. **会话服务**：记录事件、目的地和局部工作上下文，不拥有另一个长期人格记忆库。
2. **Bot 记忆服务**：以 `bot_id` 为强制边界统一保存事件记忆、事实、画像和摘要；群、用户、来源、时间与可见性作为元数据/访问约束。
3. **记忆派生任务**：嵌入、总结、画像更新使用持久任务与重试；原文成功持久化后才裁剪易失缓存。当前主上下文与消息流均在向量化失败后继续裁剪（`chat.py` 578–587 行；`context.py` 58–70 行），不能直接继承这一持久性语义。
4. **Agent 运行服务**：拥有可取消、可恢复的运行记录，显式状态、工具调用预算和 deadline；通过公开接口驱动模型。当前直接调用依赖的 `_process_with_toolcode_loop`（`chat.py` 2908–2914 行）应收敛到版本化 Provider 契约。
5. **工具服务**：声明参数 schema、所需能力、副作用类型和幂等策略；模型只能提出调用，执行授权来自运行上下文。
6. **输出服务**：把结构化响应转为平台消息，保留多段/音频发送能力，统一顺序、幂等、速率与发送结果记录。

统一 Bot 记忆不意味着任意群都自动获得所有来源原文。检索必须限定当前 Bot；来源群作为可见性与引用依据保留。同一 Bot 可以跨群回忆获准共享的知识，而每次回复仍严格绑定当前会话。这既满足全局记忆要求，也避免把平台路由权限混入提示词约定。

## 7. 对实现验收的建议场景

- 两个 Bot 同时处理同一个平台事件：人格、记忆查询、工具授权和输出路由互不串用。
- 同一 Bot 的两个群分别等待慢模型：另一个群和其他 Bot 仍能及时运行；同群重复事件不生成重复副作用。
- 生成过程中更新聊天模块：旧运行要么持有有效租约完成，要么被显式取消/迁移；新请求进入新 generation，不能访问已经销毁的旧资源。
- 新模块加载失败：旧模块仍可处理新请求；管理面能查询失败阶段与回滚结果。
- 平台发送超时但远端可能已成功：系统记录结果未知并按适配器能力核对，避免无条件重发。
- 记忆向量化失败：原始事件与提交记录保留，任务可重试，不能因裁剪上下文丢失唯一副本。
- 不同群同时更新同一用户事实：通过版本与来源解决冲突，记录可追溯结果；不将整个 Bot 的模型调用串行化。

以上属于新框架建议，不能据此声称 AliceBot 或 Forest 已实现这些保证。
