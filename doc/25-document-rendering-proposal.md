# 文档渲染方案讨论

本文为待实施的建议，不代表已存在渲染接口或媒体导入能力。

## 能力与边界

文档渲染属于插件：输入文档、排版设置及受管资源，输出图片引用。Agent 通过工具网关请求渲染，拿到引用后决定如何发送；渲染器不持有群聊会话，也不直接调用 OneBot。编译诊断作为工具结果返回给模型修改源文档，不在框架中猜测和修补错误语法。

不应因“渲染较重”就直接把它放进宿主。排版和栅格化主要是计算；真正需要外部设施的是浏览器等原生依赖。

## 引擎选择

| 输入 | 建议实现 | 依据与限制 |
|---|---|---|
| Typst | 优先验证 `typst`、`typst-render` 能否直接编译为 Forest Wasm 插件 | Typst 用 `World` 注入源码、字体和文件，栅格输出支持单页和整篇；需要实测无 JS 运行时的 Wasm 编译、包大小与资源占用 |
| Markdown 与 LaTeX 公式 | 独立插件将 Markdown 和公式交给 HTML 渲染进程，或在后续验证可靠的 Typst 转换路径 | 复用浏览器排版可较直接恢复初号机效果；Markdown、LaTeX、Typst 是不同语法，不能简单替换字符来转换 |
| HTML/CSS | 插件经 HTTP 调用独立浏览器渲染进程 | Playwright 可直接返回截图字节；Chromium 不成为内核依赖 |

Typst 的 [World](https://docs.rs/typst/latest/typst/trait.World.html) 提供资源访问边界，[typst-render](https://docs.rs/typst-render/latest/typst_render/) 提供栅格输出。[typst.ts](https://github.com/Myriad-Dreamin/typst.ts) 已有 Wasm 编译与渲染实现，说明该方向有基础，但其 JS/浏览器绑定不能直接视为 Forest ABI 成品。上述直接 Wasm 方案仍需做一个实际编译验证，不能仅据浏览器演示承诺可用。

若 Typst 直接进入 Wasm，先经宿主文件接口装入字体与声明资源，再用不可变资源集实现同步 `World`。编译期间不临时访问宿主文件系统或下载依赖；源码、字体和资源应由本次调用或模块配置明确给出。时间片仍由现有调度器处理，不增加另一套任务调度、数据库或迁移机制。

浏览器方案可以先是一项本地 HTTP 服务，接收文档并返回 PNG 字节，多页按页面返回。无需先引入任务 ID、轮询、消息队列或外部数据库。浏览器的创建、复用和关闭归服务自身管理，Wasm 插件只负责请求、诊断和媒体导入。[Playwright screenshot](https://playwright.dev/docs/screenshots) 支持直接取得图片 Buffer，无需通过 base64 文本中转。

## 受管媒体是当前需要补齐的边界

当前生成图片还不能直接接入：Memory 只管理聊天附件，Delivery 从 Memory 的 `/media/read` 解析图片；没有对渲染等生产者开放的导入契约。仅让工具返回网页 URL 或自己的宿主文件路径，无法接通这条链路。

建议把现有受管媒体能力抽为独立 Wasm 包，统一提供“写入字节并取得引用”和“按引用读取”两个操作。Memory 仍持有消息与媒体的关联，渲染插件只生产媒体，Delivery 只解析引用；宿主继续只提供通用受管文件 I/O。这样图片生成、图表和检索图片也能使用同一边界。

调用链应为：

```text
Agent → 工具网关 → 渲染插件 → 排版引擎
                          → 受管媒体 → 图片引用
Agent → CQ 图片引用 → Delivery → 受管媒体 → OneBot
```

工具结果只包含页序、图片引用、尺寸及必要诊断，图片字节不进入工具文本。原始文档与工具结果照常保留；需要向量化的内容仍由记忆流程处理。渲染插件重载不删除已经发布的媒体；媒体保留和删除由独立媒体所有者定义，不能依赖临时浏览器会话。

建议顺序是先验证纯 Wasm Typst 的最小中文/数学文档输出，确定资源代价；再落定媒体导入契约、接通图片发送；最后添加 Markdown/HTML 引擎。渲染实现和媒体拆分尚未在本轮展开。
