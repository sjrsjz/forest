# 输出额度与 Context 水位修正

## 原因

Provider 的最大输出已经设置为 16384，但旧 Agent 配置仍独立保存初始化时复制的 8192。模型请求使用后者，开启 thinking 后两次响应均以 `finish_reason=length` 截断。首次 8192 输出 token 全部用于 reasoning，重写时 reasoning 使用 7697，正文仍未完成。

另一次失败发生在模型调用之前：历史窗口 64 条、Payload 47702 字节，本地估算 24875 token，超过旧归档水位 24576。快照读取直接拒绝，使后续联合选择器没有机会省略可选历史。该错误不能证明必要消息本身装不下。

## 修正

- `agent.runtime` 5.5.0 删除配置字段 `output_tokens` 及初始化复制。报价和模型请求均使用当前请求绑定的 Provider profile `max_output_tokens`。重试、恢复仍保留原请求冻结参数。
- `conversation.scheduler` 5.1.0 的快照仅提供已核对的来源与成本事实。token、Payload、媒体与解码归档水位不再作为快照拒绝条件；快照自身的 4096 单元结构上限保留。
- 联合选择器保留必要触发与冻结因果链，在总预算中选择历史和召回；必要集合本身无法容纳时仍明确失败。Provider 不参与上下文预算或裁剪。
- 历史归档水位默认 65536，归档后保留 49152，整次模型视图估算预算 98304。设置 UI 暴露三项，拒绝保留量大于或等于水位的草稿。
- 不修改任何业务 SQL 基线，不删除记忆、人格、消息或发送记录。

## 验证

模型、配置物化与精确模型视图检查 49 项通过。Context 与 Agent 的三个隔离 PostgreSQL 包检查通过，包含超过历史水位仍可读取快照的回归。桌面浏览器验证了新默认值、非法水位阻止提交及有效配置计划。

完整链检查使用模拟模型及 OneBot，不调用真实模型、不发送真实消息。旧测试镜像在 Pillow 原生模块导入时失败，随后按当前锁定依赖重建测试镜像；该环境错误未加入业务兼容代码。

同版本镜像中的完整文本链和原生工具继续回合检查均通过：2 passed in 180.50s。文本链断言实际模型请求正文 `max_tokens=16384`，不是只检查设置值。

## 当前实例

通过正式 Worker Host 预览与选择操作先后热替换 Conversation 和 Agent，分别发布 Graph 42、43；未重启 Supervisor。Graph 43 的 25/25 模块均 ACTIVE，Agent 生效配置 r4 已无重复字段，Conversation 生效配置 r2 为 65536 / 49152 / 98304，Provider 的 16384 保持原值。前后逐字段比较确认人格和其他组件配置字段保留。

真实 WebUI 成功展示三个数值，并完成标准配置计划生成与丢弃；未提交额外改动。切换后只读核对未结算 Agent Run 为 0、发送记录仍为原 12 条 SENT，记忆来源由 1552 增长到 1576。唯一观察器恢复后的首样本 `violations=[]`。本轮没有主动重排历史失败 Run，也没有触发真实模型请求或 QQ 测试发送。
