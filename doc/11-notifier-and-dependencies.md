# 宿主事件 notifier、静态接收声明与依赖分析

本文确定 notifier 的职责：宿主产生群聊消息等事件，调度器根据模块 Manifest 中的接收声明投递到模块接口。模块是事件接收者，不是 notifier 事件的生产者；模块之间的主动通信仍使用 send/call。

本文是设计，宿主事件接入、Manifest 解析和 notifier 尚未实现。事件接收不增加模块发布接口，不建立模块之间的发布订阅系统。

## 1. 事件来自宿主

宿主侧的事件接入能力产生事件。例如，OneBot 接入收到并解析群消息后，把结构化消息交给调度器 notifier。事件类型及其 Schema 由相应宿主能力定义，不由插件 Manifest 定义或覆盖。

宿主在装载插件前具有明确的事件描述：

```rust
struct HostEventDefinition {
    source: EventSourceId,
    path: EventPath,
    schema: Schema,
}
```

EventSourceId 与 EventPath 复用合法具体 Token，分别标识宿主事件源和该源内的事件，不预设统一路径前缀。它们用于查找宿主已经提供的事件，不表示要加载一个同名 Wasm 模块。

事件产生过程与投递过程分开：宿主 OneBot 接入解释协议并构造群消息数据，notifier 只按契约和注册表投递。调度算法本身不解析 OneBot JSON，不理解消息正文含义。

OneBot 事件沿用 v11 原始字段与消息结构，仅在共享协议类型中明确省略无关字段，不另建统一聊天事件或在 notifier 内拆分、改写正文。当前只考虑单个 Bot 账号，仍保留协议里的账号、群及发送者信息，多个群聊可独立处理，见[OneBot 接入约定](04-onebot-v11.md#事件转发约定)。

宿主内部产生事件不等于为模块开放事件发布权。Wasm 没有 notify/emit/publish 宿主操作，也不能通过构造来源路径伪造宿主事件。当前设计不添加模块 events 声明。

## 2. Manifest 只声明接收入口

[Manifest](07-module-manifest.md)保留 subscriptions 必填数组，无接收声明时为 []：

```rust
struct EventSubscription {
    source: EventSourceId,
    event: EventPath,
    interface: InterfacePath,
}
```

一条声明表示：

```text
宿主事件：(source, event)
接收入口：(当前 Manifest 的 package.id, interface)
```

示意字段如下：

```json
{
  "subscriptions": [
    {
      "source": "/core/onebot",
      "event": "/group_message",
      "interface": "/group/handle"
    }
  ]
}
```

这是声明格式示例，不代表当前已经实现这些宿主事件或接口。模块必须在 provides 中声明 /group/handle，其 input 与宿主定义的群消息事件 Schema 一致。真实事件应有明确的消息结构，不能为了示例把群消息契约假定为一个 String。

目标对象由宿主绑定当前模块，不允许声明另一个模块代收。source 必须是已知宿主事件源；不能用另一个插件对象替代，形成模块事件发布通道。事件及接口路径都不接受通配符。

不提供运行中注册、订阅或取消订阅接口。模块需要改变接收范围时，通过替换 Manifest 和热重载更新；群范围等内容判断仍可由处理模块自身配置控制，不因此引入动态注册表操作。

## 3. 装载校验和注册表

宿主在 create 前检查：

- source/event 对应宿主已经提供并启用的事件。
- interface 存在于当前模块的 provides。
- 宿主事件 Schema 与接收接口 input 双向 subof，结构等价；不自动转换或投影数据。
- 接收接口的 access.callers 允许宿主登记的事件源主体调用，例如 `/core/onebot`；subscriptions 本身不授予调用权。
- 同一 Manifest 不重复声明相同的 (source, event, interface)。

接收者不另外定义事件 Schema，接收接口本身仍声明完整 output、reentrant 和 access。事件处理结果不作为同步响应返回宿主事件源；若需要请求响应，应另外使用明确的 call 契约。

有效的接收声明形成宿主内存注册表：

```text
(宿主事件源, 事件路径)
    → 宿主定义的事件 Schema
    → [(模块对象 Token, 接收接口路径), ...]
```

注册关系保存逻辑地址，不保存 Wasm 实例或函数指针。初始化成功才开放该实例的事件派发，候选声明在切换前不覆盖当前注册关系。

宿主以实际登记的事件源为直接调用主体，使用接收接口静态 AccessPolicy 的 callers 检查 Access::Call；平台发起者另行保留在可信上下文中。接收事件不自动获得配置写入或平台管理权限，不能因为通知由宿主发出就把处理器或平台用户提升为管理员，也不从普通消息字段直接授予权限。规则见[接口访问声明](06-config-access.md#21-接口声明与调用)，不增加动态授权表。

## 4. 宿主投递

事件流为：

```text
外部输入
    → 宿主事件接入解析并构造类型化数据
    → notifier 查询静态接收注册表
    → 向各模块入口提交普通请求
    → 调度器排队、推进和结算
```

这里的“普通请求”使用 send 的内部接纳与派发机制，不要求存在一个模块调用 send，也不要求源事件出现在某个插件的 uses 中。notifier 是宿主内部机制，没有模块可调用的发布 API。

每个目标独立接纳。成功只表示请求已接受，不表示处理器已经完成；QueueFull 或不可调度是该目标的提交失败，不撤销其他目标已经接受的请求，也不阻止尝试其他目标。

逐目标提交结果由宿主事件接入和管理诊断处理，不作为某个插件 notify 的返回值。没有接收者时不存入等待未来订阅者的历史队列。源事件输入无效在转发前报告，不向接收者分发不符合契约的数据。

notifier 不自动重试、丢弃旧消息腾位置或另建无限队列。宿主事件接入在目标拒绝时怎样处理上游，必须按其具体接入协议明确；不能把接纳失败解释为事件已经被成功处理。

## 5. 调度、顺序与资源归属

notifier 不直接执行来宾函数，服从[调度设计](09-scheduling.md)：

- 时间片被动暂停仍保留实例执行权，事件不能插入原推进。
- 模块主动交出执行权后，符合接口重入规则的事件任务可以开始。
- 不可重入接口被占用时，新事件可以在模块接纳额度内排队。
- 等待事件与普通 call/send 共用目标模块容量，容量不足返回 QueueFull。

同一目标按宿主实际接纳顺序排队，不根据消息时间戳重新排序；不同接收者和可重入调用不保证处理完成顺序。额外的群内排队等处理规则由接收模块实现。

网络操作完成后唤醒原任务，与群消息等宿主事件产生新的接收任务是两种机制。前者恢复既有请求，后者通过注册表选定接收接口，不能混成对当前执行实例的任意回调。

宿主事件接入的连接由相应宿主能力管理，卸载一个接收模块不等于关闭事件接入本身。模块主动通过 HTTP/WS 接口取得的资源仍归具体执行实例，按生命周期释放；notifier 不替模块保留这些连接。

## 6. 静态依赖分析

模块依赖主要由 uses 的目标对象产生。目标为另一 Wasm 模块时形成使用者到提供者的依赖边；目标为宿主原生接口时检查该宿主能力及契约可用，不推导出需要加载一个同名插件。

subscriptions 声明宿主事件接收需求，不产生“接收模块依赖事件生产插件”的边，因为这里不存在插件事件生产者。装载时只核对宿主事件支持与接收契约。配置 ACL 引用某个模块或模式也不产生加载依赖。

从外部明确启用的根模块集合计算依赖闭包，得到需要加载的模块；卸载分析沿反向依赖关系给出受影响对象。Manifest 解析不自动安装或启动模块，正式加载管理再执行计划，也不擅自修改用户启用意图。

无依赖环时，依赖先于使用者初始化、卸载顺序相反。依赖环的接纳与启动规则另行确定，不在本轮引入运行时死锁检测。

模块 trap 后只标记故障模块不可调度、结算相关调用并回收资源，不自动级联卸载依赖方。静态依赖声明仍然存在，恢复等待外部热重载或卸载。

## 7. 卸载与替换

[三种卸载方式](10-module-lifecycle.md)统一作用于普通请求和 notifier 投递。热重载关闭旧入口后，新事件按有界队列规则留给新实例；容量不足明确拒绝。候选未初始化成功，不派发到候选，也不向新旧实例重复投递。

成功切换时替换该模块的接收注册关系。Manifest 去掉某条接收声明，只影响之后按新表选取的事件，不追溯撤销已经接纳的消息；增加接收声明也不补发历史事件。这是宿主替换声明，不是运行时取消订阅 API。

普通 trap 后不再向故障模块积压事件。宿主接入和 notifier 可以继续为其他健康模块投递，故障目标按不可调度报告。宿主资源回收、call 失败结算及禁止自动恢复遵守生命周期文档。

本阶段没有独立事件分发插件、模块事件发布、消息持久化、确认协议、自动重试、过滤表达式或历史回放。模块需要互相请求处理时，直接使用已经明确的 send/call。
