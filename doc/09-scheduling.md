# 模块任务、执行权与宿主锁

同一 Wasm 实例一次只推进一个任务。时间片被动让出保留实例执行权；SDK 正常返回 Pending 才释放执行权。跨主动让出点的互斥由模块显式使用 `lock(token)` / `unlock(token)` 表达，不在 Manifest 中声明接口重入属性。

运行与 ABI 见[运行说明](13-runtime-and-sdk.md)，所有权转换见[状态机](12-scheduler-state-machine.md)，停止方式见[生命周期](10-module-lifecycle.md)。调度器不引入普通 call 取消、自动超时、死锁检测、优先级或已开始任务迁移。

## 1. 调度单位

| 概念 | 含义 |
| --- | --- |
| 模块对象 | Manifest 声明的稳定单例身份 |
| 执行实例 | 当前一代 Wasm 内存、全局状态和执行资源 |
| 请求 | 已接纳但尚未首次获得执行权的宿主 FIFO 项 |
| 任务 | 已绑定实例的一次接口处理，保存输入、上下文和可恢复进度 |
| 一次推进 | 开始或恢复指定任务，直到主动让出、完成或失败，并完成 ABI 收尾 |
| 实例执行权 | 独占推进实例及操作其来宾内存的权利 |
| 宿主锁 | 按具体 Token 命名、由一个任务独占的逻辑资源 |

不同任务共享同一实例的内存，但不会同时执行来宾指令。不同实例可以并行推进，任务不绑定固定操作系统线程。

## 2. 两种让出

### 2.1 时间片被动让出

Wasmtime 暂停当前异步导出调用时，原调用栈、完整 ABI 推进、执行权、已持有的宿主锁全部保留。执行线程可以处理其他实例；同实例的另一任务、alloc/free 或 destroy 都不能插入。恢复时继续同一个 Wasmtime Future。

被动让出可以发生在一次状态修改中间，不表示事务边界，也不产生热重载交接条件。普通时间片使用可恢复 yield，不以 trap 实现。

### 2.2 模块主动让出

模块任务在 SDK 中保存后续进度，导出调用正常返回 `Step::Pending`，宿主完成本次 ABI 收尾后，执行权才交还调度器。原任务、来源、宿主操作关联和所持锁仍然存在。同实例其他就绪任务或请求随后可以推进。

宿主函数调用本身不是主动让出。已完成的操作可以立即返回；宿主 Rust Future 的 Pending 也不能单独开放 Store。模块必须在真正返回 Pending 时允许其他任务访问未锁定的共享状态，不保留冲突借用。

## 3. 两层 Future

SDK 使用来宾 Future 保存完整异步处理器；宿主每次只要求 SDK 推进指定任务一次。一次完整宿主推进包含输入分配与复制、invoke/poll、输出读取和缓冲区释放。

| 观察 | 执行权 |
| --- | --- |
| Wasmtime Future 返回 Pending，包括 epoch 暂停 | 继续属于原推进 |
| Wasmtime 调用完成，SDK 返回 Pending | ABI 收尾后释放 |
| SDK 返回 Ready，包括模块自身 Err | 输出与 ABI 收尾后释放 |
| Wasmtime trap 或执行失败 | 终止整个实例，进入宿主回收 |

宿主不为多个完整异步处理器同时保留独立的 Store 调用栈。主动让出后，上一个 Wasmtime 调用已经结束，下一次推进才重新进入实例。

## 4. 宿主操作与唤醒

1. 模块提交操作，宿主绑定具体实例和当前任务，复制输入数据。
2. 结果已经就绪时，SDK 直接取走并继续当前推进。
3. 结果未就绪时，SDK 登记实际 Future 的唤醒关系；返回 Pending 后才让出。
4. 后台完成只写宿主完成槽、通知任务，不直接进入 Wasm 或修改来宾内存。
5. 任务再次取得执行权后读取结果。

开始推进时消费已有通知；推进期间到达的新通知保留。返回 Pending 时不再清空通知，因此不会丢失交权前到达的完成事件。通知可以去重，不能产生两个并行推进。任务退休后的迟到通知不能指向下一代实例。

## 5. 显式宿主锁

```rust
lock(key: Token) -> DispatchResult<()>
unlock(key: Token) -> DispatchResult<()>
```

每个 Wasm 实例持有独立锁表，只有同实例内相同具体 Token 才表示同一把锁。其他实例及热重载后的新实例使用自己的锁表，相同锁名互不影响。持有者是宿主确定的 `(实例, 任务)`；模块不能指定持有者或替其他任务解锁。Token 在这里是锁名，不赋予配置或接口访问权限，也不暴露宿主内部互斥锁。

锁为独占、非递归、FIFO，只协调实例内部任务。实例 trap/Force 时整实例停止，锁表随实例回收，不保留毒化锁给其他实例。空闲时立即授予；否则当前任务异步等待，正常返回 Pending 后其他任务仍可推进。再次获取自己已持有的锁同样等待，不自动增加递归计数。等待顺序按宿主收到 lock 的顺序登记，不由后台任务启动顺序决定。

许可有明确的唯一归属：

```text
等待操作 → 已授予的完成槽 → 任务持有表 → 释放
```

`operation_take` 成功将结果写入来宾内存后，才把许可从完成槽移交给任务。取消未完成操作会退出 FIFO；取消已授予但未取走的操作会直接释放许可。任务取走结果以后，取消结果句柄不再释放已持有的锁。非持有者 `unlock` 返回 `Denied`。

Rust SDK 的 `host::lock(key).await?` 返回 `LockGuard`，离开作用域同步解锁，也可以 `guard.unlock()?` 显式解锁。所有权仍属于根来宾任务，移动 guard 不转移宿主所有权。遗漏释放由任务结束时的宿主回收处理。

create/destroy 禁止 lock/unlock。生命周期没有普通接口的竞争需求，也不能让初始化或清理依赖另一个普通任务释放锁。

同实例多个接口访问共同状态时，可以使用同一个锁名；同一接口处理互不相关的资源时，可以按资源生成不同锁名。锁的范围由代码中的实际临界区决定，不依赖包配置是否正确描述了并发行为。

## 6. 接纳与任务选择

普通请求池覆盖已接纳请求、工作中和等待中的任务及必要收尾。I/O 通知有独立、同样有数量与字节上限的池，防止等待回执的普通调用占满通知名额；发布后激活另有一个控制槽。数量或输入字节额度不足时，原子返回 `QueueFull`；不入队、不撤销已有请求、不另建无界等待队列。名额随唯一 Admission 移动，只有实际收尾后才归还。

请求位于接口 FIFO；开始时移出队首，绑定实例和任务，把执行权交给该任务。后续请求可以在该任务主动让出后开始；需要互斥的处理器在代码中获取相同宿主锁。等待锁的任务已执行过 Wasm，仍占接纳额度。

实例驱动器按以下规则推进：

1. 已有未返回的完整推进时，只恢复原 Wasmtime Future。
2. 实例空闲时，从去重就绪序列选择 `Start(interface)` 或 `Resume(task)`。
3. Start 消费对应 FIFO 队首；队列非空时把下一 Start 排到就绪序列尾部。
4. SDK Pending 保存任务；Ready 消费返回出口并完成必要收尾。
5. 还有就绪工作时继续轮转；没有工作时等待通知。

同接口请求按接纳顺序开始。新请求与已就绪任务按就绪顺序参与调度，没有接口闸门或重复的 ready 布尔状态。一个同步死循环持续持有本实例执行权，不能同时在本实例启动第二个死循环；epoch 机制仍允许其他实例运行。

## 7. 示例

A、B 两个接口共同修改一份状态，均在临界区获取 `/state`：

| 时刻 | 动作 | 实例执行权 | 宿主锁 |
| --- | --- | --- | --- |
| 1 | A1 获取锁并修改状态 | A1 | A1 |
| 2 | A1 时间片暂停，A2/B1 到达 | 仍归 A1，新请求排队 | A1 |
| 3 | A1 等待 HTTP，SDK 返回 Pending | 释放 | A1 |
| 4 | A2 开始并等待同一锁，返回 Pending | 释放 | A1 |
| 5 | B1 开始并等待同一锁，返回 Pending | 释放 | A1 |
| 6 | HTTP 完成，A1 恢复、提交状态、释放 guard | A1，随后释放 | 授予 A2 的完成槽 |
| 7 | A2 恢复、取走许可并进入临界区 | A2 | A2 |

不使用此锁的查询接口可以在第 3 步后正常推进。锁不会阻塞执行线程，也不会停止同实例所有其他接口。

## 8. 保证与责任

一次推进不与同实例其他推进交错；锁保证同名临界区的任务级独占。模块负责选择一致的锁名和范围、结束 `RefCell` 借用、安排外部写入与解锁顺序。宿主不分析状态含义或自动合流读写结果。

配置仍是独立原子的单项 get/set/reset。实例内的逻辑锁不约束其他模块或管理员修改宿主配置，也不把分开的操作变成数据库事务。模块 call 等待环或交叉持锁可能形成死锁，调度器不自动探测、重试或解锁。

## 9. 生命周期和错误边界

create 完成并发布前不运行普通请求；destroy 仅在普通来宾任务停止后运行。两者禁止 send/call 和 lock/unlock，其他能力见[宿主接口](08-host-interfaces.md)。

默认 Drain 的管理请求在 Waiting 期间保持旧实例接纳与推进。重载等整组已开始任务及其收尾结束后，在首次领取下一请求前原子提交。宿主 FIFO 中尚未开始的 Object 请求交给新实例首次执行，保留额度、来源、返回出口和同接口 FIFO。等待锁的任务已经开始，不能随未启动请求迁移。Instance 通知和激活即使未启动也不能交接，Drain 必须等其额度全部归还；空闲原生监听不占任务。卸载没有后继实例，须完成全部接纳请求。

AtYield 在完整推进返回后停止恢复剩余任务，先等待已提交的不可中断本地操作，再运行受限 destroy。Force/trap 终止整个实例：未返回的 call 结算为调度异常，所有来宾任务停止，不再调用任何 poll/free/destroy，也不恢复仍在等待锁的任务。

宿主清理取消锁等待与尚未交付的许可；已经持有的锁等所属任务不可中断的原生操作结束后才回收，避免下一持有者与旧文件或 SQLite 写入重叠。旧实例全部真实资源释放后才可创建下一代。已经提交给其他模块或远端的操作不承诺递归取消或回滚。

Preparing / Waiting 的管理请求可以外部取消；Committed 不回滚。持续工作或持锁等待可以使 Drain 一直 Waiting，只有外部明确选择 AtYield/Force 才改变停止方式。
