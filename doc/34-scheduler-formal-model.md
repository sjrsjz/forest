# 调度系统的形式化模型

本文使用带标签的状态转换系统描述 Forest 的执行、通信和生命周期，并分析允许静态依赖环后的重载问题。模型对应现行集合管理策略，并保留被替代路由的反例作对照。

当前实现允许静态依赖环，默认等待目标集合自然静止后提交，并支持提交前取消、整组初始化与统一发布。call trace 尚未引入，也不是本策略的前提。下文区分现行规则与用于对照的旧交接方案。现行执行语义见[模块调度](09-scheduling.md)，资源所有权见[调度器状态机](12-scheduler-state-machine.md)。

Store/ABI 和重载交接的 Lean 工程及其已检查定理见[调度器 Lean 验证](35-scheduler-lean-verification.md)。该工程证明所定义协议的性质；实际 Rust 到模型的对应目前经过人工审查，尚无自动细化证明。

## 1. 建模范围与三种关系

系统中至少存在三种不同的关系：

| 关系 | 顶点 | 边的含义 | 是否描述实际等待 |
| --- | --- | --- | --- |
| 静态依赖 | 模块对象 | Manifest 的 uses 指向目标接口 | 否 |
| 调用祖先 | 一次具体调用 | 本次请求由哪一个调用提交 | 否；调用方不一定正在等待它 |
| 必要前置条件 | 完成事件、许可、激活条件等 | 一个条件成立前，另一个条件必须先成立 | 是；用于证明具体阻塞 |

call trace 描述第二种关系。接口占用、排队和重载屏障也可能构成第三种关系，但不会因此出现在 call trace 中。

普通通信不设置隐含超时，不自动重试、取消或重放。重载作为可取消的管理请求，在不可逆提交前接受外部取消；可选的管理截止时间也只产生同一种取消输入，不给普通 call 增加超时，不自动升级为 Force。模型尚未选择自动死锁检测策略。

本轮分析限于调度器可观察的未结算 call、请求队列、宿主锁、执行权及生命周期屏障。不要求判断 Wasm 是否终止、理解模块内部循环，或推测经 send、外部服务和模块共享状态建立的应用协议。等待没有结束，不等于调度器已经证明存在死锁。

模型主体是 Wasm 模块调度。OneBot 与其他插件一样是普通 Wasm 实例。通用网络等原生操作通过宿主操作 $O$ 的提交与完成表示。若原生接口也有串行许可或等待其他模块，其资源等待同样可以加入第 10 节的分析；不能一概假定原生调用必然立即完成。

## 2. 对象、实例、请求与任务

设：

- $M$：稳定模块对象的集合，元素 $m$ 以 Token 标识。
- $I_m$：对象 $m$ 的接口路径集合。接口地址为 $(m,i)$。
- $G$：Wasm 执行实例的集合，$owner:G\to M$ 给出其稳定对象。
- $R$：已被接纳的请求标识集合。
- $T$：已开始的普通任务标识集合。
- $J$：管理重载请求的标识集合；系统请求由普通接口请求 $R$ 与管理请求 $J$ 区分载荷。

实例标识与任务标识仅供宿主内部关联，不是 Manifest 版本，也不是新的插件寻址路径。同一个对象在重载前后的实例不同；同一个实例上的多个调用任务也不同。

每个请求 $r$ 携带：

$$
r=(id,m,i,input,context,kind,trace)
$$

其中 $kind\in\{call,send\}$；$context$ 保留宿主绑定的 origin 和 caller。trace 在当前实现中不存在，在候选模型中使用第 6 节的定义。

请求与任务分开：排队请求没有来宾 Future；开始执行后才建立任务 $t$，且 $request(t)=r$。同一个请求至多建立一次任务，不因唤醒、时间片或重载再次建立任务。

接口声明不携带并发策略。普通任务在主动让出点交错；需要跨该边界互斥的代码显式调用 lock/unlock，持有者由宿主绑定到具体实例与任务。

## 3. 全局状态

系统是一个带标签的状态转换系统：

$$
\mathcal S=(States,Labels,\longrightarrow),\qquad
\Sigma\xrightarrow{a}\Sigma'
$$

一次转换表示一个可排序的宿主状态操作、一次来宾计算步骤或一个外部完成通知。不表示整个异步处理器是原子执行的。

采用以下抽象状态：

$$
\Sigma=(D,J,Q,H,T,X,N,O,L,K,F,\mu)
$$

| 分量 | 含义 |
| --- | --- |
| $D$ | 对象目录：阶段、当前实例、已发布声明与停止后的去向 |
| $J$ | 重载请求及其目标实例、候选包、停止方式与提交状态 |
| $Q_{g,i}$ | 实例 $g$ 的接口 $i$ 已接纳、未开始的请求 FIFO |
| $H_m$ | 对象 $m$ 等待下一实例的有界交接队列 |
| $T$ | 未完成任务的实例、接口、请求和控制阶段；包括正常完成后的必要收尾 |
| $X$ | 实例当前独占推进的持有者，$X(g)$ 为空或指向唯一任务 |
| $N_g$ | 实例的去重就绪序列，元素为 $Start(i)$ 或 $Resume(t)$ |
| $O$ | 宿主操作及其所属任务、完成槽和必须终结的资源 |
| $L$ | 每个实例独立的锁表，按具体 Token 命名：FIFO 等待操作，以及完成槽或任务持有的唯一许可 |
| $K$ | 请求或任务已退出普通执行，但仍持有接纳额度等资源的回收工作 |
| $F$ | 已结算结果的规格记录，用于表达“至多一次”；不是要求实现保留终态表 |
| $\mu_g$ | 实例共享的来宾内存、全局值和任务内部进度 |

这是数学分解，不要求实现复制这些事实。例如任务的实例身份是 $T$ 的投影；锁是否空闲由其唯一许可归属导出，不再维护第二份 held 布尔值。

目录阶段为 Creating、Serving、Stopping、Destroying、Releasing、Staged、Failed；未装载表示目录中没有对应活动项。重载是停止后的去向，携带候选包与交接队列，不另外叠加 reloading 布尔值。

create、destroy 和初始化中的 ABI 入口使用特殊任务符号 $c_g,d_g$，复用同一个独占推进规则，不能获取或释放普通任务的宿主锁。

不同实例可以同时持有各自的 $X(g)$。物理并行度 $P$ 只限制同一时刻实际运行的推进数不超过 $P$；它不改变实例内的互斥关系。

每个模块的计算行为由参数关系 $\mathcal P_g$ 给出：在持有 $X(g)$ 时，它可以改变自己的 $\mu_g$、提交宿主操作、返回 Pending、返回输出或 trap。模型不预设处理器一定终止，也不要求宿主分析模块程序。共享配置和真实 I/O 的值属于宿主或环境；它们通过相应操作转换进入模块可观察的结果。

## 4. 执行与宿主锁

### 4.1 任务持有的宿主锁

对任意实例 g 内的锁名 k，状态为 FIFO 等待操作与至多一个许可归属；不同 g 的锁表不共享：

$$
L_{g,k}=(W_{g,k},P_{g,k}),\quad
P_{g,k}\in\{\bot,Granted(o),Held(t)\}
$$

LOCK 按宿主导入顺序将操作放入 FIFO。空闲时只允许队首获得 Granted；TAKE 成功复制结果后，将 Granted 转为所属任务的 Held。取消未交付操作移除等待项或释放 Granted，不释放已经交付给任务的 Held。UNLOCK 仅接受相同实例与任务，其他主体返回 Denied。

主动或被动让出都不改变 Held。任务回收在其不可中断原生工作结束后释放残留 Held；trap/Force 停止整个实例的所有来宾任务，先取消等待，再由宿主收尾释放持有锁。锁等待属于已经 START 的任务，不能交给新实例首次执行。

### 4.2 开始任务

若实例处于 Serving 或 Drain 中的 Stopping，实例可以选取普通工作；其他停止方式不继续选取旧工作。

对于 $Q_{g,i}$ 的队首请求 $r$，开始条件为：

$$
X(g)=\bot
\ \land\ OrdinaryDispatchAllowed(g)
$$

OrdinaryDispatchAllowed 排除生命周期关闭及上一任务必要收尾阶段；不按接口属性阻挡新请求。

START 转换原子地完成：从 FIFO 移出队首、建立任务 $t$、消费 $Start(i)$ 并将执行权交给 $t$。该接口若还有请求，可将 $Start(i)$ 重新排到就绪序列尾部。候选准备完毕且目标集合满足第 7 节提交条件时，先执行 COMMIT，不再在旧实例开始下一请求；这项选择与 START 由同一目录锁排序。

未取得执行权的请求只有宿主表示。START 之后，即使物理时间片尚未轮到，也已经绑定具体实例并按未完成任务处理；不追踪第一条 Wasm 指令来反推能否交接。

### 4.3 两种让出

| 转换 | 变化 | 保留内容 |
| --- | --- | --- |
| PREEMPT：时间片被动让出 | 当前推进暂时不占用物理执行机会 | $X(g)=t$、来宾调用栈、任务、所持宿主锁 |
| YIELD：SDK 返回 Pending 且 ABI 收尾完成 | $X(g):=\bot$；任务保存其进度 | 原任务、请求、所持宿主锁、宿主操作关联 |
| READY：SDK 返回有效输出且 ABI 收尾完成 | $X(g):=\bot$；任务进入正常结算及必要收尾 | 收尾完成前仍保留相关许可和额度 |

PREEMPT 后同实例只能继续原推进，不能选另一个任务。YIELD 后同实例才可以开始或恢复其他允许的任务。

宿主函数被调用、宿主 Rust Future 返回 Pending、日志写入或 I/O 提交，都不单独构成 YIELD。只有来宾推进正常返回 SDK 的 Pending 并完成 ABI 收尾，才释放实例执行权。

### 4.4 唤醒

WAKE 将 $Resume(t)$ 放入 $N_g$；序列去重。开始推进时消费已有的 Resume 通知，推进期间到达的新通知保留。

因此，任务在返回 Pending 前收到通知时不会丢失唤醒。任务已退休时，迟到通知不产生新任务，也不能唤醒下一实例中编号恰好相同的任务。

READY 不表示宿主操作本身必然成功；模块返回 Err 同样是正常输出。trap 与 Force 使用失败路径，不能假定仍可调用来宾 free 或 destroy。

### 4.5 转换规则的写法

用 $update(\Sigma,\ldots)$ 表示只修改列出的状态分量，其他分量保持不变。以下规则给出执行核心的操作语义；接口策略和生命周期作为前置条件参与，不另写一套执行器。

对于 START，设 $Q_{g,i}=r::q$，$Start(i)$ 是下一项允许开始的就绪工作，$t$ 为新任务标识：

$$
\frac{X(g)=\bot\quad OrdinaryDispatchAllowed(g)}
{\Sigma\xrightarrow{Start(g,i,t)}
 update(\Sigma,Q_{g,i}:=q,T:=T\cup\{t\mapsto(g,i,r,Guest)\},X(g):=t)}
$$

该转换还消费对应 Start 通知，并按队列剩余情况更新就绪序列。宿主锁只由模块显式操作取得，不参与 START 的接纳与选择。

对于已开始任务的 RESUME，要求 $Resume(t)$ 位于可选择的就绪位置、$t$ 属于 $g$，且普通调度允许：

$$
\frac{X(g)=\bot\quad Resume(t)\in N_g}
{\Sigma\xrightarrow{Resume(t)}
 update(\Sigma,X(g):=t,N_g:=N_g\setminus\{Resume(t)\})}
$$

PREEMPT 对逻辑任务、宿主锁与执行权的状态是恒等转换，仅改变物理执行机会；恢复时继续同一推进。YIELD 则在合法的 SDK/ABI 边界将 $X(g)$ 清空，不移除 $T(t)$ 或已持有宿主锁。

FINISH 的前置条件是任务已返回有效输出且必须结束的本地操作已经终结。它消费结果出口、释放残留锁和额度、移除任务；锁释放可唤醒其 FIFO 队首等待者。异常回收可以拆成“先消费结果出口、再在 $K$ 中释放资源”两个阶段，但不重复结算。

这些规则忽略同一转换中的不相关字段更新，而不忽略其原子性。实际就绪项选择须遵循序列顺序；公式中的集合差只表示移除该项，不表示重新排序其余元素。

## 5. 接纳、call 与 send

### 5.1 原子接纳

模块提交宿主操作与宿主实际接纳请求是两个动作。调用方在提交后可以继续当前推进；是否真正挂起，取决于之后是否返回 SDK Pending。

ADMIT 在控制边界检查目标、Schema、uses、callers、阶段与容量，并选择 $Q$ 或 $H$。成功时一次性预留额度并入队；失败时完成调用方的宿主操作错误，不留下已接纳请求。

设 $B_m$ 为对象 $m$ 仍持有接纳额度的请求集合，包含 $Q$、$H$、普通任务和必要回收中的请求，则：

$$
|B_m|\leq limitCount_m,
\qquad
\sum_{r\in B_m}charge(r)\leq limitBytes_m
$$

charge 为接纳时计入预算的输入大小。重载不重置稳定对象的这笔账目。容量不足直接返回 QueueFull；不存在“先在无限队列等容量”的隐含步骤。

### 5.2 call

call 接纳成功后，其宿主操作等待目标请求的结算。结算结果为调度层 Result，成功载荷仍是接口声明的模块 Result。

只有调用方确实等待这项结果时，它才形成任务完成的前置条件。仅仅提交 call 不足以证明调用方正在等它；并行 Future、select、结果已就绪以及等待出口被丢弃，都必须按实际处理逻辑分析。

目标已经接纳的请求属于接收方。调用方退出或关闭等待出口，不自动撤销目标执行，也不重放其已发生的副作用。

### 5.3 send

send 的宿主操作在接纳成功时完成，不等待目标执行结果。目标后续失败进入诊断，不再通过 send 返回。

因此，对 send 本身有：

$$
CompleteAdmission(send(r))
\not\Rightarrow CompleteExecution(r)
$$

如果模块在 send 之后另行等待“回复消息”或共享状态变化，那是它另建的等待协议；框架不能仅凭 send 自动推导该关系。

## 6. 候选扩展：调用祖先与 call trace

定义一个宿主生成的调用帧：

$$
frame(t)=(owner(instance(t)),instance(t),t)
$$

对外部进入的新请求，$trace(r)=\epsilon$。任务 $t$ 产生新请求 $r'$ 时：

$$
trace(r')=
\begin{cases}
trace(request(t))\mathbin{\|}[frame(t)],&kind(r')=call\\
\epsilon,&kind(r')=send
\end{cases}
$$

符号 $\|$ 表示序列拼接。实际模块路径序列是该帧序列向 Token 的投影。

trace 由宿主继承，模块不能伪造。send 清空 trace 不清空 origin，也不改变宿主对直接 caller 的绑定。

调用祖先关系按实际创建先后严格向前，因此即使模块对象路径出现 $A\to B\to A$，具体调用的祖先关系仍然无环：第二次 A 是另一次调用。它可以分叉，不要求每个任务只提交一个 call。

trace 中的帧可能在之后失效。例如调用方放弃等待，但目标请求仍继续执行。用于重载路由时必须确认帧对应的任务和实例仍然存活，不能因 trace 保存了一个 Token 就延长旧实例生命。

**结果仍通过请求自身的一次性返回出口回到相应宿主操作。** trace 不替代返回出口，不让回包逐层按模块名称重新查找接收者。

## 7. 自然静止集合重载

### 7.1 入口路由

| 状态 | 通过权限、类型和容量检查的新请求 |
| --- | --- |
| Serving，包括 Preparing / Waiting 管理请求期间 | 进入当前实例的 $Q_{g,i}$ |
| reload 已提交，旧实例停止、清理、回收或 Staged | 进入 $H_m$ |
| reload 的候选 Creating，包括成功后等待发布 | 进入 $H_m$ |
| 首次装载的 Creating、卸载中或 Failed | 返回对应调度错误 |

管理请求等待期间不建立交接队列、不冻结已经空闲的某个成员，也不对调用祖先给予特别路由。直到整组同时静止，才原子提交并关闭全部旧入口。

### 7.2 自然静止

对旧实例 g，数学条件为：

$$
Quiet(g)\iff T_g=\varnothing
\land X(g)=\bot\land CleanupPending(g)=\varnothing
$$

尚未 START 的 $Q_g$ 不影响来宾内存，没有来宾 Future，可以交给新实例首次执行；Quiet 不要求该队列为空。Drain 卸载没有后继实例，其条件另加 $Q_g=\varnothing$。

实现通过接纳凭据归属表达同一事实。对 Serving 实例，所有排队请求、未完成任务和必须结束的请求收尾仍持有 Admission；驱动器在 ABI 和任务本地操作收尾完成之后才归还它。令 $UsedRequests(g)$ 和 $UsedBytes(g)$ 为当前占用额度，重载时可判定：

$$
UsedRequests(g)=|Q_g|\quad\land\quad
UsedBytes(g)=\sum_{r\in Q_g}|inputBytes(r)|
$$

也就是扣除宿主 FIFO 仍持有的份额后，两种在途额度都为零。不新增任务计数，不要求未启动请求先执行或归还额度。卸载则仍要求两种占用均为零。

物理归还请求额度和输入额度都完成后才发送静止通知。取消等待操作不伪造额度归还。

静止不要求删除模块配置、关闭所有闲置连接，也不要求其他模块停止持有其 Token。已经在其他模块独立执行的 send 不因来源对象重载而被递归排空。

### 7.3 整组提交

对一组目标 S：

$$
Quiet(S)=\bigwedge_{m\in S}Quiet(g_m)
$$

默认 Drain 的提交条件：

$$
CanCommit(j,\Sigma)=CandidateReady(j,\Sigma)
\land SameTargets(j,\Sigma)\land Quiet(S)
$$

CandidateReady 表示当前联合候选目录满足类型、权限声明与替换条件。SameTargets 表示每个对象仍是准备时的实例，或是装载请求保留的空位/Failed 对象。初次装载不需要等待旧实例；卸载集合也需要保证预期目录中没有组外使用者。

检查、将请求改为 Committed、转移未启动队列和整组旧入口关闭在同一控制转换中完成。START 先发生会使 Quiet 为假，必须等该任务完成；只有接纳而未 START 的请求不阻止提交。

Drain 重载提交时，将每个 $Q_{g,i}$ 按同接口 FIFO 顺序移入对象的 $H_m$，旧 FIFO 清空。转移只改变请求的宿主归属，保留原输入、来源、返回通道与 Admission，不运行来宾代码，不再次接纳或重新鉴权；旧 Start 通知随旧实例释放。提交后新请求追加到 $H_m$，发布新实例后按接口重建就绪通知。原请求至多经历一次 START，不会在新旧实例重复执行。检查为空后不能释放控制权，再使用旧判断执行替换。

提交时还将候选声明纳入管理操作的预期目录；其他管理请求不能趁其尚未发布而卸掉候选所需的接口提供者。

### 7.4 请求状态与取消

管理请求具有：

$$
Preparing\longrightarrow Waiting\longrightarrow Committed
\longrightarrow Succeeded\ \text{或}\ Failed
$$

$$
Preparing/Waiting\longrightarrow Cancelled\ \text{或}\ Failed
$$

Preparing / Waiting 请求与对象的 Serving 阶段并存。取消只撤销本次管理意图；旧入口和普通队列从未关闭，所以没有队列回滚或工作重放。

取消与提交由同一控制边界排序：先取消则该请求失去后续提交权，包括迟到的读取、编译结果；先提交则取消返回“已提交”。取消不需要运行 Wasm，不依赖模块主动让出。

请求成功与否不在受理时预测。持续有已开始但未结束的工作时可以一直 Waiting；只有未启动积压不阻止重载。由外部明确取消或改选 Force。运行时没有默认等待期限，普通 call 不因此增加超时。

AtYield / Force 是显式的有损选择，通过候选检查后可以提交；驱动器随后在完整推进边界处理 AtYield，或通过运行时中断处理 Force。提交授权这些动作，不表示原任务已经自行完成。

### 7.5 替换的类型条件

每个旧接口保留，并满足：

$$
Input_{old}\preceq Input_{new},
\qquad Output_{new}\preceq Output_{old}
$$

$\preceq$ 为 Schema 子类型关系，Output 包括完整的模块 Result。配置保持原有键集合与等价 Schema，默认值可以更新，全部当前值保留。

所有组内候选按同一预期目录检查，不能逐包只针对旧目录检查。组外使用者也必须得到它们声明的契约。类型兼容不证明实现行为相同，也不是跨多次调用的版本事务。

### 7.6 旧实例释放与候选发布

提交后所有旧成员先停止、清理并完成宿主资源回收。Releasing 中不可中断的本地写入必须终结；完成后进入 Staged，表示逻辑对象保留，但旧实例已经释放。

只有全部旧成员都到达 Staged，才安装整组配置声明并创建候选。所有声明默认值在任何 create 运行前就已存在；声明失败时尚无来宾执行，整组结束为失败。每个候选完成 create 后等待一次性发布许可；期间仍不运行普通任务。

全部候选成功且未被中断后，在一个控制转换中发布整组 Manifest、ACL 和 Serving 入口，再通知驱动器开始普通工作。某个候选失败时整组不发布，其他候选清理后一起进入失败状态。旧实现已经销毁，不自动回滚。

统一发布只保证不存在“某个新入口已经开放，另一个候选还未初始化成功”的状态，不保证调用者跨多次独立调用始终观察同一批实现。

### 7.7 当前策略排除的屏障环

在 Preparing / Waiting 期间，普通请求的接纳与可执行性不因本次重载而改变。提交时目标组的旧普通任务已经全部结束：

$$
Committed(j)\Longrightarrow \forall m\in S:T_{g_m}=\varnothing
$$

因此旧任务不可能仍等待因这次提交而进入 $H_m$ 的回调。这排除了第 11 节的特定重载屏障环。生命周期又禁止 send/call，不会通过这些接口产生旧任务与新 create/destroy 之间的模块调用环。

该结论仅针对调度器可观测的模块通信与入口屏障。它不证明任意普通调用程序无死锁，也不预测外部 HTTP 服务或模块内部计算何时结束。

## 8. 静态依赖与加载

静态图定义为：

$$
G_D=(M,E_D),\qquad
(a,b)\in E_D\iff a\text{ 的 uses 引用了 }b\text{ 的接口}
$$

规划器允许该图存在任意有向环；闭包中仍检查目标、输入输出契约与宿主事件支持。

输入启用集合 $Roots$ 后，待加载闭包通过可达性求得；图有环不妨碍闭包计算。记录已访问对象即可，不依赖拓扑排序。

由于 create 不允许模块间 send/call，先在联合候选目录上完成链接检查，再初始化整批待加载模块，全部成功后统一开放入口。单模块 load 也是只有一个目标的管理请求。

统一开放入口只保证装载过程不向外暴露半组普通接口。初始化已经提交的配置或外部 I/O 不是可回滚事务。

强连通分量可以帮助展示依赖关系和组织装卸集合；它不自动成为执行锁、内存共享单元或必须整体重载的实体。

## 9. 安全性与活性

### 9.1 安全性不变量

以下性质适合作为转换规则的归纳检查目标：

1. **执行互斥**：$X$ 对每个实例至多有一个持有者；只有该持有者能推进或访问其来宾执行状态。
2. **许可唯一**：每个实例内的锁名至多有一个许可，归尚未交付的完成槽或具体实例与任务持有。
3. **请求唯一归属**：每个仍持有额度的请求恰好位于一个接口 FIFO、交接队列、任务或回收对象中，不重复入队。
4. **接纳有界**：对象计数和输入大小预算始终满足第 5 节的不等式。
5. **结算至多一次**：每个请求的结果出口至多被消费一次；已经关闭的出口不被重新绑定。
6. **跨实例隔离**：宿主操作结果关联到准确的实例与任务，不按稳定 Token 交给下一实例。
7. **停止顺序**：旧来宾执行结束且必要本地操作终结后，才允许下一实例 create。
8. **阶段限制**：create/destroy 中不接纳被禁止的 send/call 或 lock/unlock；权限检查不因处于生命周期阶段而放宽。

返回结果与归还接纳额度不是同一个事实。异常路径可以先结算调用者，再在 $K$ 中完成必要回收；不能因此提前将仍持有资源的请求从预算中删除。

这些是形式化规格的检查目标。本文没有完成对全部 Rust 实现的机械验证，不将上述列表表述为已证明的整库定理。

### 9.2 活性需要额外前提

无条件的“每次 call 最终返回”不是现行规则提供的保证。本轮只研究可观测调度关系及重载的可取消性，不为模块内部计算或外部 I/O 的终止作证明。

公平性只能要求持续可执行的工作最终获得执行机会：

$$
ContinuouslyEnabled(a)\Longrightarrow EventuallyScheduled(a)
$$

它不把等待许可的任务变成可执行任务，不使网络必然完成，也不解开重载屏障。

对有限、必要等待关系无环的工作，若各次本地推进终止、外部等待最终完成、调度公平且没有新工作无限延长相关集合，可以按前置条件顺序证明这些工作最终结束。这里每个前提都必须明确，不能仅凭静态模块图为 DAG 得出结论。

## 10. 必要前置条件模型

### 10.1 为什么不直接把所有 pending call 画成死锁图

任务可能使用 select 等待多个条件之一，也可能等待全部并行结果。所有已提交操作不等于所有必需条件。

分析时可用等待公式 $\varphi_t$ 表达任务当前继续推进所需的条件，例如：

- $Done(r)$：必须等一个调用结果。
- $Done(r_1)\land Done(r_2)$：必须等两个结果。
- $Done(r_1)\lor IOReady(o)$：任一条件即可继续。

这些公式是分析者给出的模块语义，不要求宿主反射 Rust Future、推测模块控制流或增加动态字典协议。具体反例只使用单个不可选的 await，因此不需要分析任意模块。

### 10.2 必要前置边

写作：

$$
u\leadsto v
$$

表示：在给定分析条件下，事件或条件 $u$ 要成立，尚未满足的 $v$ 必须先成立。顶点可以是任务完成、宿主锁可用、新实例发布或旧实例排空。

例如：

$$
Finish(t)\leadsto Done(r)
$$

只在任务必须等待该结果才能完成时成立。对于有其他可完成分支的 select，不能因为其中包含这个 call 就添加该必要边。

若全部顶点尚未满足，且存在一圈严格的必要前置关系：

$$
u_0\leadsto u_1\leadsto\cdots\leadsto u_k\leadsto u_0
$$

并且没有圈外事件或允许的替代转换能解除其中的必要关系，那么圈内条件不能由正常执行首先满足。这给出了局部阻塞的证明；系统其他模块仍可能继续执行。

普通等待图中“画出一个圈”不自动满足上述条件。OR 分支、可独立到达的外部完成事件、主动释放资源及管理中断，都可能破坏所谓的必要性。

本文讨论的内生死锁排除管理员随后发出 Force 等干预。若把始终可能到来的外部强制中断也算作正常进展，便不能再把“没有任何可能的下一步”当成这些调用的死锁定义。

### 10.3 本轮采用的可观测关系

可观测图 $G_{obs}(\Sigma)$ 只取宿主已有事实：

- 任务 t 拥有尚未结算的 call，请求目标为 r。
- 已接纳请求 r 仍未开始，或已由目标任务执行；任务可能等待某个锁名。
- 该宿主锁当前由哪一个完成槽或具体实例与任务持有。
- 请求 r 因重载 j 被放入交接队列。
- 管理请求 j 正在等待哪些旧任务、队列或当前推进退出。

这些边不要求解析模块内部程序。模块只提交操作而未实际等待结果，或采用 select 等多个结果组合时，未结算 call 不能自动被提升为第 10.2 节的必要前置边。因此观察到环可以作为保守的结构性阻塞信号，不能据此擅自中断普通调用或宣称已经证明任意模块死锁。

暂未结束的外部 I/O 和没有交回的来宾推进作为待完成条件保留，不根据持续时间猜测它们是否已经卡死。管理请求仍可经独立宿主控制入口取消，不依赖目标模块处理一条取消消息。

## 11. 提前截断入口策略的可达反例

本节保留一个被当前策略排除的反例，便于比较。旧路由 $\rho_{trace}$ 在旧任务尚未结束时提前关闭入口：带旧祖先的回调进入旧实例，其他新请求进入交接队列。它不是当前实现。

### 11.1 声明与任务

- A 提供 `/start` 和 `/callback`，两者是不同接口。
- B 的 `/work` 处理器在代码中获取共同锁 `/work`。
- A.start 调用 B.work；B.work 在其执行分支中可能调用 A.callback。
- 所有调用都通过 Schema、ACL 和容量检查。
- 讨论期间没有 Force、trap、取消或其他可替代的完成分支。

B 的不同请求可以走不同分支：B₁ 先等待 I/O，再 await A.callback；B₂ 在取得许可后直接完成。因此该例不依赖无限递归或无限计算。

### 11.2 可达序列

| 步骤 | 动作 | 形成的事实 |
| --- | --- | --- |
| 1 | 外部独立请求启动 B₁；B₁ 等待 I/O 并主动让出 | B₁ 持有 `/work` 锁，trace 为空 |
| 2 | 另一外部请求启动 A₁；A₁ call B.work，产生 B₂ | B₂ 已开始并等待 `/work` 锁，trace 为 $[frame(A_1)]$；A₁ 等待 B₂ |
| 3 | 外部对 A 发起 Drain 重载 | A₁ 留在旧 A，普通新工作转向交接队列 |
| 4 | B₁ 的 I/O 完成；B₁ call A.callback，产生请求 C | C 的 trace 为 $[frame(B_1)]$，没有旧 A 的存活祖先，因此进入 $H_A$ |
| 5 | B₁ 必须等待 C，主动让出 | 两个实例都没有能解开该环的普通就绪工作 |

在步骤 5，原 I/O 已完成；等待环不依赖它永远不返回。A.callback 原本可以开始，但其请求没有进入旧实例 FIFO。

必要关系为：

$$
Finish(A_1)
\leadsto Done(B_2)
\leadsto Finish(B_1)
\leadsto Done(C)
\leadsto Publish(A_{new})
\leadsto Empty(A_{old})
\leadsto Finish(A_1)
$$

其中 $Done(B_2)\leadsto Finish(B_1)$ 来自 B.work 处理器显式获取的共同锁，$Publish(A_{new})\leadsto Empty(A_{old})$ 来自重载屏障。

```mermaid
flowchart LR
    A1[旧 A 的 A₁ 完成] --> B2[B₂ 完成]
    B2 --> B1[B₁ 结束并释放许可]
    B1 --> C[A.callback 请求完成]
    C --> New[新 A 发布]
    New --> Empty[旧 A 排空]
    Empty --> A1
```

在该旧路由下，若不进行重载，C 可以进入旧 A 的 `/callback` 并完成，随后依次结束 B₁、B₂、A₁。该例说明提前建立交接屏障会新增等待边；当前自然静止策略不执行步骤 3 中的入口截断。

### 11.3 call trace 能证明什么

如果 B₁ 本身来自旧 A 的存活调用，C 的 trace 就包含旧 A，$\rho_{trace}$ 会将它送入旧实例，前述具体环被解除。

但本例中的 B₁ 与 A₁ 是独立进入系统的调用。B₂ 排在 B₁ 后面，没有让 B₁ 成为 A₁ 的调用后代。

因此：

$$
CallAncestry\neq NecessaryPrerequisites
$$

“仅允许有旧实例祖先的请求进入旧实例”不能保证所有原本可完成的调用都不因 Drain 重载而卡住。

### 11.4 自然静止策略如何排除该执行

当前策略允许把本次重载登记为 Waiting，但 A₁ 仍存活时，提交条件为假，不能关闭旧 A 入口。步骤 4 的 C 因而直接进入旧 A 的 callback 队列，而不是 $H_A$。

C、B₁、B₂、A₁ 可以按普通调度依次结束；只有之后整组静止，才允许提交重载。这里不需要 call trace，也不需要先取消管理请求来恢复普通调用。

若普通模块自己还有其他可观测等待关系，管理请求可以继续 Waiting 并由外部取消。没有“等待足够久后猜测旧模块已经不可恢复”的隐含转换。

## 12. 当前设计结论

1. 静态图允许环，接口契约仍在联合目录中检查。
2. 请求与任务分开；未开始请求、已开始任务与锁等待分别保留准确归属。
3. 默认重载等待整组自然静止；等待期间不改变旧实例的入口。
4. 静止检查与整组提交原子排序，提交后所有旧成员先释放，候选全部成功再统一发布。
5. Pending 管理请求可取消；Committed 不回滚旧实例。AtYield / Force 必须明确选择。
6. 安全性、调度公平性、普通调用最终完成和管理请求成功是不同命题。

当前没有引入 call trace、通用死锁检测、默认期限、普通 call 自动取消或新旧实例共享内存。静态环支持不意味着普通调用等待环被自动解开。
